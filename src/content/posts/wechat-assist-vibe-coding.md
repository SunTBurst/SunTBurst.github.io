我的日常工作，离不开沟通。

我在央国企项目中做商务合同相关工作。合同谈判、采购协调、内部请示、对外澄清，每件事背后都有很多人，也有不同的立场和语气。同一句话，对领导、同事、供应商和合作方，表达方式往往完全不同。有时我已经知道要传递什么信息，却还要反复想：这句话会不会太硬，边界有没有说清楚，对方看完会不会误解，既要坚持立场又怎样留出合作空间。

这种消耗很难用“打字慢”来概括。真正费心的是组织表达，是在关系、场景、目标和风险之间做判断。忙碌的时候，一条看似普通的微信回复，也可能占用不少注意力。

于是我开始做一个给自己用的微信沟通助手。

如果你更关心软件怎样配置和操作，可以直接看[微信沟通助手配置与使用教程](/posts/wechat-assist-setup-guide/)。

## 我想解决的不是代聊，而是表达前的那段思考

市面上已经有很多聊天机器人，但我的需求更具体：我需要先说明自己真正想表达的意思，让工具参考联系人、当前场景和历史上下文，生成几条有差别的候选回复。最终选哪一条、还要怎样改、是否发出，决定权始终在我。

这也决定了产品的基本边界。它不是替我经营关系的机器人，而是一张放在微信旁边的“表达草稿纸”。默认流程是生成候选、继续修改、复制，再由我回到微信确认和发送。自动回复被单独放在实验功能里，默认关闭；即使开启相关配置，只要发送能力没有得到可靠验证，结果仍应先落为草稿。

我把回复方式收敛成三种：情绪导向、工作导向、通用兼顾。关系类型则作为另一条独立信息保存。面对同一个联系人，我可以在需要安慰时选择情绪导向，也可以在讨论合同节点时切到工作导向。这样比简单地把聊天分成“工作”和“生活”更贴近真实情况。

## 我在 Vibe Coding 中扮演什么角色

这个工具是我主导的一次 Vibe Coding 实践。

我不把 Vibe Coding 理解成对 AI 说一句“帮我做个软件”，然后等待成品。我的工作是把实际问题讲清楚，持续判断什么值得做、什么不该做，并把每一轮结果放回真实使用场景里检查。AI 帮我分析、设计和写代码，我负责需求、取舍与验收。

例如，早期界面曾经有多套主题和较多技术选项。实际审视后，我发现自己每天需要的只有一条清楚的路径：打开回复工作台，选择联系人，说出意图，得到候选，继续修改。于是我要求主界面只保留“回复、联系人、我的资料、设置”，把模型、连接器和诊断信息放进高级设置与调试中心。这个变化不是为了追求某种设计潮流，而是因为工具每天都要用，主流程必须安静、直接。

我也坚持把“我的资料”和“联系人画像”分开。我的表达习惯、工作背景和固定偏好是一份长期资料；不同联系人的关系、称呼、沟通禁忌和偏好是另一份资料。AI 可以给出画像建议，但建议需要我确认，不能覆盖手工填写的内容。

完整提示词同样需要可编辑。软件内置的业务规则不是藏在代码里的黑箱：我可以查看整份正文、暂存修改、试用效果、正式应用，也可以回到默认版本或历史版本。新规则只影响之后的新请求，已经生成的候选仍保留原来的版本依据。

这些决定看起来不像“写代码”，却直接决定软件最后是否能用。Vibe Coding 对我最有价值的地方，是让我能把日常工作中形成的判断，逐步变成可操作的产品规则。

## 从能演示，到可以作为个人工具继续打磨

项目最初只是一个回复助手的想法，后来逐步形成 Windows 桌面应用。开发过程中，我不断把演示效果和真实能力分开：静态页面只能证明布局，离线夹具只能证明流程，程序成功启动也不能证明它已经读到了真实聊天，更不能证明它可以安全发送。

2026 年 9 月，软件完成了一轮较大的可用性改造。新的单一界面接入了回复工作台、可搜索的联系人库、本人资料、联系人画像、完整回复规则编辑、连续修改和版本记录，也补上了本地备份与恢复。

随后我在配置模型时遇到一个很实际的问题：界面显示已经配置，调用却返回 401。排查后发现，问题不只是密钥本身，还包括服务、接口地址和密钥所属平台的对应关系。Kimi Code 订阅和 Kimi 开放平台使用不同的地址与 Key，切换服务时也不应该沿用另一家的凭据。

修复后的版本按 Provider 和 API 地址隔离凭据，增加了独立的 Kimi Code 订阅选项，并继续把真实 Key 放在 Windows 安全存储中，不写入普通配置文件。DeepSeek 与 Kimi Code 已通过合成资料完成实际鉴权和三条候选回复生成。这里的“合成资料”很重要：它证明模型配置链路能工作，但不等于真实微信聊天已经完成验收。

我还希望在不调用云服务时使用本地模型。现在选择 LM Studio 后，软件会自动读取本机可用的对话模型，也保留手动填写模型名称的入口。当前版本的生产回复引擎已经连接本机 LM Studio，由已加载的 `google/gemma-4-e4b` 完成健康检查，并基于合成对话生成三条候选回复。本地模型的速度和效果仍取决于电脑配置、模型大小与加载状态。

OpenClaw 则保留为可选的本机编排方式。应用支持将 Gateway Token 放进独立安全存储，并隔离 OpenClaw 与普通模型 Provider 的端点和凭据；保存普通 Provider 配置也可以切回直接模型。我的电脑目前只有 OpenClaw Companion，没有实际运行的 OpenClaw Gateway，因此这里只能确认配置边界，不能声称真实 OpenClaw 已经联通。

## 现在它能做什么

目前的核心使用方式已经比较清楚：

- 在“我的资料”中保存自己的背景、语气和表达偏好；
- 在“联系人”中维护不同对象的关系和沟通画像；
- 在“回复”中选择联系人和回复模式，写下真正想表达的意思；
- 从多条候选中选择一条，用自然语言要求“更简短一点”“语气缓和，但保留时间要求”等，继续生成 V2、V3；
- 复制满意的候选，回到微信检查并发送；
- 在“设置 → 回复规则”中查看和调整完整业务提示词；
- 将本机数据库、已确认画像和当前生效规则做成加密备份。

软件当前只面向 Windows 和我自己的使用场景。源码保存在 GitHub 私有仓库，不公开发布；每个可测试版本都会保留独立程序包、源码与验证记录。

## 我仍然保留的边界

当前版本仍有 7 项 Windows 安装环境相关检查没有通过，因此这不是一份“全绿”的测试报告。干净分发包也不附带可选的微信上下文连接组件；使用微信上下文前，需要使用者自行具备受信任、兼容的本机连接组件。只有模型、没有可用的联系人和对话上下文时，软件不会编造一段聊天来生成看似真实的回复。

真实微信的完整读取、窗口交互、填入和发送也没有全部验收。

我愿意公开记录这些边界，因为个人工具也需要诚实。能生成回复，不代表能稳定连接微信；能找到窗口，不代表能读取完整聊天；能配置自动回复，也不代表应该让它无人看管地发送。

这款工具还在继续打磨。它已经把我脑中一部分反复发生的沟通判断，变成了可以编辑、可以回退、可以逐版确认的流程。对我来说，这就是这次 Vibe Coding 最实在的结果：我提出真实问题，AI 加快实现，我持续做选择，并为最终结果负责。

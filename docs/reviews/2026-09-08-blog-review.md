# SunTBurst 博客现状评估与调整建议

评估日期：2026-09-08。源码基线：`adf3513`。本文为建议稿，记录本轮核查结果和可供选择的改造方案；不表示后台或新主题已经实现。

## 当前有效方案：免费 GitHub 托管与最小改动

已细化为 [详细实施方案与日常操作说明](../superpowers/plans/2026-09-08-minimal-github-blog.md)，包含用户需要做的操作、六项实施任务和逐步验收结果。

用户最新约束：只使用免费 GitHub 作为博客托管，不额外架设服务器，优先复用已有代码。以下方案取代此前 CMS、私有内容仓库发布链、Supabase 内容后台和 Umami 组合建议；后面的原始评估保留作问题依据，不再作为实施范围。

### 技术基线

继续使用当前单仓库、Astro、Markdown 和 GitHub Pages / Actions。保留 `public/images/avatar.svg`、蓝黄品牌、现有文章地址和内容集合。默认不新增数据库、OAuth 服务、Cloudflare Worker、付费模型、常驻服务器或第二个内容仓库。

### 最小改动对应的目标效果

| 原需求 | 当前推荐实现 | 实际边界 |
| --- | --- | --- |
| 从博客发帖 | 博客提供“新建文章”“新建随记”入口，打开 GitHub 对应目录的新建文件页；提供可复制的 Markdown 属性模板 | 编辑发生在 GitHub，自带登录、预览和保存；不伪装为站内一体化编辑器 |
| 修改文章 | 在文章适当位置提供“在 GitHub 编辑”链接，准确映射原文件 | GitHub 决定是否有写权限；访客不能直接修改博主仓库 |
| 上传图片 | 入口指向现有 `public/images` 上传页面；保留当前 Markdown 图片约定 | 从 Obsidian 只粘贴文字不会上传本地附件，需要同时上传图片 |
| 集中管理 | 一个轻量工具页或页脚管理菜单，汇集新建、文章目录、图片、站点配置、Actions 和 GitHub 管理链接 | 该静态入口可能被访客打开，真正受保护的写操作在 GitHub；不称为私密后台 |
| 草稿 | 私密草稿继续留在本地 Obsidian，准备公开后再放入仓库 | 公开仓库内的 `draft: true` 或分支都不能保护原文隐私 |
| 发布结果 | 复用现有 Actions 工作流和构建状态页，提供准确的发布任务入口 | GitHub 编辑器预览不等于 Astro 正式效果；提交不等于部署成功 |
| 首页简洁 | 复用 HomeHero、现有文章列表和 ActivityStream，将最近文章前移，缩减重复导览；工具留在已有实验室等页面 | 保留原内容和旧地址，不进行目录级重构 |
| 阅读轻松 | 文章页使用现有 `hidePageBanner` 能力减少重复横幅；减轻底色、边框和阴影；空目录不显示 | 保留原 LOGO、阅读增强和必要交互，不更换整套主题 |
| 正文搜索 | 在现有公开索引中补充正文搜索字段，扩展 UnifiedSearch 的匹配范围 | 首版不引入 Pagefind；继续沿用现有键盘交互与静态数据 |
| 背景与外观 | 将实际要调整的少量选项集中到现有配置或样式变量，通过 GitHub 修改后自动发布 | 不开发拖拽换肤后台，也不把访客本机主题切换当成全站配置 |
| 访问情况 | 保留现有内容、页面及构建统计 | GitHub 仓库 Traffic 是仓库访问，不能冒充博客访客 PV/UV；严格仅 GitHub 的首版不承诺完整访客分析 |
| 评论 | 若启用交流，优先考虑跳转 GitHub Discussions；维持现有 Supabase 功能不启用 | 此交流方式不能满足原先的 AI 审核后才公开，不将其称为等价替换；不擅自启用 |

### 仅保留为备选的功能

- **站内编辑器**：Sveltia 有不部署 OAuth 服务的 token 登录方式，可以作为后续选项。但需要维护 CMS、处理浏览器中的仓库访问令牌、验证 Markdown 和图片兼容性；不是本轮最小改动的首选。不需要先开发自有 CMS，也不在此轮创建或配置访问令牌。
- **嵌入式评论**：Giscus 无需博主自建服务器，数据保存在 GitHub Discussions，但嵌入组件与认证会依赖 giscus.app 及其 GitHub App。如果“仅 GitHub”也排除第三方托管组件，则使用普通 Discussions 链接。两者都不具备原方案的发布前 AI 审核。
- **Pagefind、知识图谱、复杂 Obsidian 转换、云端草稿和自动配图**：首版不引入，避免把少量页面调整扩展成新平台建设。

### 实施范围

1. 首页与导航：主要复用 `src/components/home/PortalHome.astro`、`HomeHero.astro`、`src/config/navigation.ts` 和现有导航组件。调整排序与入口，避免重写模块。
2. 阅读与样式：主要调整 `src/pages/posts/[id].astro`、现有 Layout 属性及 `src/index.css`。不因简化横幅而顺手迁移全部框架依赖。
3. 编辑入口：在现有配置中记录仓库信息，新增少量链接或一个轻量工具页；复用文章内容元数据定位文件。
4. 搜索：复用 `src/utils/portalIndex.ts`、`src/types/portal.ts` 和 `UnifiedSearch.svelte`，正文来自已发布内容，搜索字段不进入收藏存储。
5. 文档与验证：代码实施后更新 README；验证正文关键词、草稿过滤、编辑链接、旧地址与桌面/手机显示。现有布局断言应按新目标调整，保留内容与权限相关测试。

本轮是方案修订，只修改两份评估/调研文档，没有开始上述应用代码改动，也没有部署变更。

## 1. 当前方向

用户希望博客简洁、清晰、轻松，主要通过从 Obsidian 粘贴 Markdown 来发布内容，需要只有博主能使用的编辑和管理功能。用户选择了“温暖纸页”的氛围，同时明确表示喜欢现有 LOGO，并要求先考察现有风格。

因此建议保留现有 `public/images/avatar.svg` 的 TS 图形、蓝黄配色和 SunTBurst 名称。温暖纸页用于调整底色、留白和阅读排版，蓝黄继续承担品牌识别。此前三种风格对比图是探索示意，其中的示例文章、标语和替代字标均不是已确定的个人内容或品牌方案。

总体建议：围绕写作、发布、阅读、评论形成完整流程，把低频工具和运维信息放到次级入口。公开知识平台、多人协作和私有 RAG 作为独立后续项目讨论。

## 3. 现有风格如何保留和减轻

现有设计采用 Toy Brick Brutalism，主要特征是蓝黄配色、方形卡片、粗描边、硬阴影和粗字重。它有辨识度，适合在 LOGO 和少量重点操作上保留。全页面反复使用相同强度时，标题、按钮、统计与正文会互相争夺注意力。

| 元素 | 建议 |
| --- | --- |
| LOGO | 保留原 SVG 图形及颜色，不重新生成或替换。检查导航外围重复边框能否减轻。 |
| 色彩 | 保留蓝色与浅黄；大面积底色采用浅米白，正文采用深灰。灰绿不作为默认主色替换品牌蓝。 |
| 卡片 | 多数改成留白、细分隔线或轻描边。硬阴影仅用于少量重点元素。 |
| 字体 | 正文保持清晰的中文无衬线字体；减少大面积粗体。标题可试用稍有书卷感的字体，需与现有字标共同预览后确定。 |
| 首页图片 | 可用一张适量留白的插画或照片表达轻松氛围，放在介绍区域；图片不铺在正文文字下面。 |
| 文章页 | 移除重复的大站名横幅，保留一次标题和必要元信息；正文栏建议约 720–800px，手机端保留舒适边距。 |
| 目录 | 仅对有足够层级的长文显示。手机端折叠，短文不显示空目录。 |
| 动效 | 减少持续装饰动画和进入动画，保留必要的状态反馈及轻微悬停反馈。 |

建议的视觉基准为“现有蓝黄品牌＋浅米白纸页”。先做首页、长文阅读页和后台编辑页三个关键页面的预览，再推广到其他页面。

## 4. 访客侧的信息架构

建议主要入口为：点击 LOGO 返回首页，导航保留“文章、随记、关于”，加搜索和深浅色切换。“项目”在有持续更新的实际内容后可增加独立入口。

首页的建议顺序：简短个人介绍和适量图片 → 最新文章 → 最近随记 → 简短页脚。置顶文章作为可选配置。文章较少时按实际数量展示，不用建设日志或示例文章填满。

| 当前功能 | 建议归属 |
| --- | --- |
| 文章、知识、主题 | 统一放在文章浏览入口下，通过内容类型和专题区分；暂不机械合并 Markdown 集合，保留原 URL。 |
| 说说 | 对外可称“随记”，保留独立轻量列表。 |
| 动态、现在、站点更新 | 个人近况可纳入关于或随记；技术建设日志保留次级入口或放到后台。 |
| 分类、标签、归档、日历、时间线 | 统一到文章页的筛选和归档入口，避免五组独立主导航。 |
| 天气、随机图片、声音、GitHub 活动、随机漫游 | 如继续保留，集中在一个次级工具页面，退出首页核心区域。 |
| 站点数据、构建状态 | 后台概览；需要公开时只保留简洁状态页。 |
| RSS、友链、隐私 | 简短页脚或关于页。 |
| 未启用能力说明 | 在后台显示配置状态；公开页面不反复展示大块“准备中”。 |

调整入口不等于立即删除已有内容。旧地址需保留或重定向，避免破坏外链、收藏和评论绑定。

## 5. 博主管理与 Markdown 编辑器

博主与访客阅读相同的已公开文章是合理的。需要补充的是身份验证后的管理权限、未发布内容及编辑操作。

后台建议只设置五组入口：

| 入口 | 首版范围 |
| --- | --- |
| 概览 | 新建文章、待处理评论、最近发布结果；接入真实统计后展示浏览趋势、热门文章及来源。 |
| 内容 | 文章和随记，草稿、已发布、编辑、预览、撤回、历史版本和导出 Markdown。 |
| 评论 | 待审核、已公开、已拒绝等列表，以及回复和处理记录；复用已有评论能力。 |
| 素材 | 图片上传、替代文字、封面选择、引用位置及重复文件处理。 |
| 设置 | 个人介绍、导航、主题预设、首页图片、背景、功能开关。访客深浅色偏好与全站配置分开保存。 |

编辑器默认采用 Markdown 源码和即时预览，支持纯编辑和纯预览模式。使用成熟编辑器组件，自行实现与本站内容模型相关的功能，不自研底层文本编辑器。中文输入法、撤销重做、长文性能、表格、代码、公式和手机编辑应作为选型验证内容。

Obsidian 导入应包括：

- 粘贴 Markdown 和导入 `.md`，读取 frontmatter 并映射标题、日期、标签、分类和封面。保留无法识别的属性或清楚提示，避免静默丢失。
- 支持图片粘贴、拖入和文章与附件一并导入。仅粘贴文字不会自动把电脑中的本地图片上传到网站。
- 解析 `[[笔记]]`、带别名双链、标题锚点及 `![[图片]]`；只链接已公开目标。缺失或私有目标列出待处理项，不自动发布关联笔记。
- 明确 callout、公式、代码和表格的兼容范围。Dataview、插件脚本及动态查询不承诺直接运行；嵌入笔记需要转换为经选择的公开快照。
- 自动保存私有草稿、导出备份、发布前检查失效图片和链接。后台预览与正式渲染使用相同的兼容规则和安全处理。
- 保存使用版本标识处理冲突。重复粘贴、跨设备编辑和本地文件修改不得直接覆盖更新版本。

## 6. 可选的技术路线

| 方案 | 优点 | 代价及限制 |
| --- | --- | --- |
| A：现有静态博客＋轻量定制后台（推荐） | 保留 Astro、文章 URL 与 Pages；围绕 Obsidian 适配，评论、素材、外观可以统一管理。 | 需要完成后台权限、私有存储及发布服务；发布需要等待构建与部署。 |
| B：接入成熟 Git CMS，例如 Decap | 较快获得内容编辑、图片上传和 Git 发布流程。 | 评论、访问统计和全站外观仍需整合；Obsidian 扩展需适配，公开仓库中的草稿分支不能保密。 |
| C：改为数据库驱动的动态博客 | 发布后可立即读取更新，管理体验容易一体化。 | 需调整当前托管及内容来源，迁移和日常运维范围更大。 |

GitHub Pages 是静态托管服务，无法独自提供受保护的数据写入和服务端权限验证。因此后台必须配套独立服务。建议复用已选择的 Supabase 身份、数据库和存储技术，公开页面继续静态生成。

推荐路线的数据关系：

```text
Obsidian 粘贴或 Markdown 导入
            ↓
博主后台：编辑、私有草稿、版本、素材和外观设置
            ↓  仅在明确发布时生成公开快照
受保护的发布服务
            ↓
Git 仓库中的已发布 Markdown 和公开资源
            ↓
Astro 构建 → GitHub Pages → 访客阅读
```

具体约束：

1. 首版只有一个博主角色，不提前建设成员审批、多工作区或多人协作。
2. 后台推荐独立来源部署，从博客的管理入口打开，延续统一视觉。沿用既有公开站点与私有应用隔离的方向，具体地址尚未确定。
3. 登录页可以公开；草稿、素材和每项管理接口必须验证博主身份。隐藏菜单、`noindex` 和前端标记都不构成权限控制。
4. 草稿和未公开附件进入受权限保护的私有存储。当前 `draft: true` 只排除网页构建；文件若提交到公开仓库，原文仍可被读取。
5. 新后台作为编辑来源，公开仓库作为发布快照；现有文章先导入并保留路径。后续直接修改仓库时应检测版本冲突，不建立两个互相覆盖的编辑源。
6. 发布状态区分“已保存、发布中、已上线、发布失败”。仅在对应版本部署成功后显示已上线；失败保留上一个可读版本并支持重试。
7. 发布文章、资源、索引和评论目标要保持一致；撤回文章应同步处理搜索、RSS、站点地图和评论目标。公开 Git 历史中的内容无法通过普通撤稿保证彻底消失。
8. 全站外观设置也采用保存、预览和发布流程，避免把仅在博主浏览器里变化的效果称为全站换肤。
9. 访问统计使用真实数据源，统计范围和口径明确；不采集后台及草稿访问，不将未配置显示为真实的零访问。具体服务、预算及同意机制尚待选定。

## 8. 实施顺序与验收

1. **确定关键页面和导航**：保留原 LOGO，预览简化后的首页、长文页和编辑页；确认视觉与核心范围。
2. **完成写作发布闭环**：验证博主登录、导入 Markdown 与图片、私有草稿、预览、发布、编辑和再次发布。验收结果为一篇真实文章能全流程上线。
3. **整合评论、素材和设置**：复用现有评论服务；完成全站背景和封面的保存与发布；独立接入真实访问统计。
4. **完成结构收敛与兼容**：统一内容索引、列表组件、主题变量、文档及旧地址；后台和草稿不得进入公开产物。

核心验收包括：匿名和普通登录用户直接请求后台接口仍被拒绝；未公开内容不出现在源码快照、搜索、RSS、sitemap、公开附件和日志中；多设备编辑不静默覆盖；发布失败有明确状态且不误报上线；手机首屏能更快进入正文；已有文章 URL 和评论关联保持有效。

# 个人博客第一阶段设计

## 1. 目标与范围

本项目在保留 ImUpXuu/xuhome 的“Toy Brick Brutalism（积木粗野主义）”视觉语言基础上，建立一个可独立维护的个人静态博客。

第一阶段只交付不依赖外部后端的静态核心：文章、说说、标签、分类、归档、搜索、RSS、sitemap、关于页、响应式布局、深浅色主题和 GitHub Pages 发布准备。

AI 问答、评论、访问统计、天气、随机图片、邮件订阅、自动友链、音乐、在线状态和任何外部 API 均不在第一阶段启用。它们将在基础站点稳定后，以用户自有服务为前提单独设计和接入。

## 2. 采用方案与边界

### 2.1 方案比较

1. **清洁化复用上游代码骨架（采用）**：保留页面结构、视觉组件和静态内容体系；移除上游内容、身份、外部服务和工作流，并在新仓库中建立独立历史。
2. **从零重写相近视觉**：版权边界最简单，但需要较多时间重建页面、交互和响应式细节。
3. **直接 Fork 后修改**：不采用。它会保留上游历史、内容和有风险的自动化，且难以避免作者域名及服务残留。

本项目采用方案 1。上游 README 声明代码（不含 `src/content/`）可按 MIT 用作模板、内容保留所有权利；但根目录未提供正式 LICENSE。因此第一阶段必须保留来源说明，且不得复制或发布上游文章、说说、图片、头像、友链、账号、音乐与服务数据。公开发布前应向上游确认许可证文本或获得明确授权。

### 2.2 不可变安全边界

- 不复制上游 `src/content/**`、`public/images/me.jpg` 或其他个人素材。
- 不保留 SSH/rsync、固定服务器 IP、Cloudflare 清缓存、自动友链、订阅推送、压测等 GitHub Actions。
- 不向任何 `*.upxuu.com` 或作者控制的 API 发送新站内容、访客数据或对话数据。
- 不配置远程 Git 仓库、不发布网站、不使用用户凭据；这些动作需要后续的显式授权和账号信息。

## 3. 第一阶段架构

```text
src/content/posts/*.md ─┐
src/content/talks/*.md ─┼─> Astro 静态构建 ─> dist/ ─> GitHub Pages
src/config/site.ts ─────┤
public/（自有图标和图片）┘
```

- 框架：Astro 静态输出，保留必要的 React/Svelte islands 与 Tailwind 视觉组件。
- 内容：Markdown 为唯一内容来源；文章和说说分别使用明确的 Zod schema。
- 配置：站点身份、导航、SEO、主题、页脚和功能开关收敛到 `src/config/site.ts`；构建 URL 从 `PUBLIC_SITE_URL` 读取，本地开发使用有效的示例 URL。
- 页面：首页、文章详情、说说、归档、标签、分类、关于、友链、隐私、404、RSS、sitemap、robots。
- 搜索：仅搜索已构建到客户端的本站文章/说说数据，不调用外部搜索服务。

## 4. GitHub Pages 部署设计

默认目标是 GitHub Pages 的用户站点仓库：`<GitHub 用户名>.github.io`。这样当前以 `/` 开头的站内链接不需要承担项目子路径兼容复杂度。

- 使用新的最小权限 GitHub Actions 工作流：签出、使用固定 Node/pnpm、冻结依赖安装、构建、上传 `dist/`、部署 Pages。
- 工作流在构建时提供 `PUBLIC_SITE_URL=https://<repository_owner>.github.io`。
- 若用户未来选择项目站点或自定义域名，先修改 `PUBLIC_SITE_URL`、Astro `site/base` 配置并逐页验证再发布；不在本阶段猜测用户名或域名。
- Vercel middleware、Vercel headers 和 Cloudflare Worker 配置不进入第一阶段，因为 GitHub Pages 不执行它们。

## 5. 内容模型

### 文章

必填字段：`title`、`published`。

可选字段：`description`、`image`、`tags`、`category`、`slug`、`draft`。

文章页面在构建期生成，按发布时间排序；缺少描述时从正文提取短摘要，缺少封面时使用本地默认封面或不显示图片，不访问随机图片服务。

### 说说

必填字段：`published`。

可选字段：`title`、`tags`、`location`、`weather`、`mood`、`device`、`slug`、`draft`。

`weather` 是作者手工填写的文本字段，不调用天气 API。

## 6. 外部功能的后续接口边界

第一阶段将通过显式开关隐藏或移除所有外部功能。第二阶段若启用，应遵守以下边界：

- 评论：仅连接用户自有 Waline 服务，评论审核与隐私政策由用户配置。
- 统计：仅连接用户自有或明确选择的统计服务，默认不加载追踪脚本。
- AI：使用用户自有 API 代理；不得将密钥放在前端，不默认发送全文或会话记录。
- 天气、随机图片和订阅：均需选择可控、HTTPS、具备可接受隐私边界的服务后才实施。
- 自动友链：采用 Issue 收集、人工审核和 PR 合并；禁止将 Issue 输入拼接进 shell 命令。

## 7. 验收标准

1. 全站不含 `upxuu.com`、上游作者账号、固定服务器地址或上游内容文件的运行时依赖。
2. 不含上游高风险工作流；Pages 工作流只访问 GitHub 官方部署能力。
3. 新增一篇文章和一条说说后，首页、详情、标签/分类、归档、RSS 和 sitemap 均能在构建产物中反映。
4. 文章 frontmatter 缺少必填字段或字段类型错误时，构建期能给出明确错误。
5. 依赖树被锁定，说明文档列出本地开发、内容发布和 Pages 部署前置条件。
6. 不在本地或远程执行任何发布动作；真实 GitHub 用户名、仓库和域名由用户后续提供。

## 8. 已知限制

- 当前开发环境未检测到 Node.js，因此本轮可完成源码与配置的静态审查；完整 `pnpm lint` / `pnpm build` 需在安装 Node.js 22 和 pnpm 后执行。
- 上游视觉组件很丰富，第一阶段优先保证核心页面完整与无外部依赖；不影响文章阅读的个别装饰性组件可以延后恢复。
